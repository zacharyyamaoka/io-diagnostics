Three traps every proposal has to close

The tree has one parent edge per entity (part_of or via). summarize() collapses a problem into the nearest failed ancestor on that edge.16 Three probes ran against the real contract code, with no host process and no hardware:

Trap 1: the Computer's checks written on host swallow the rack

$ python3 -B knockon_probe.py
--- Computer checks ON host
  chip counts (independent causes): {'error': 1}
  knock_on: [('host/usb1/1-3/can/15', 'host')]
  CAN 15 row: level=error · counted as its own cause: False
--- Computer checks on sibling host/computer
  chip counts (independent causes): {'error': 2}
  knock_on: []
  CAN 15 row: level=error · counted as its own cause: True

A full disk becomes "the cause", and CAN 15's fault 33 becomes its symptom. The computer lane in flight already guards against this: it evaluates the host's own records as a leaf host/:self beside its children. The comment there says "a hot CPU or a crashed computer plugin explains nothing about a dead CAN bus".19

Trap 2: a rig row beside the tree counts one missing board twice

$ python3 -B rig_doublecount_probe.py
independent causes counted by the chip: {'warn': 1, 'error': 1}
knock_on: []

Two records describe one fact:

  • the rig row's ExpectedMissing, an entity via host that is not an ancestor of the board (expected.py _rig_row);17
  • the board's own BoardNotAnswering, at ERROR in the moteus driver.23

The chip reads "IO 2 ⚠".

Trap 3: a composite that reports ERROR hides its failed member

$ python3 -B spider_probe.py
spider self-reports WARN  -> chip names: cell/spider/leg3 · counts {'warn': 1, 'error': 1} · knock_on []
spider self-reports ERROR -> chip names: cell/spider · counts {'error': 1} · knock_on [('cell/spider/leg3', 'cell/spider')]

When the spider reports WARN, its record and the leg's are counted as two causes. When it reports ERROR, leg 3 (fault 33), which the spider's own message names, is filed as the spider's symptom.

The shared fix (record v0.2, additive), which every proposal below assumes:

  • The field: DiagnosticStatus.caused_by: tuple[str, ...], a list of entity paths. It is stripped by to_diagnostic_status(), so stock → v0 → stock stays the identity.
  • The rule:
    • A record whose every caused_by member is itself a non-OK independent cause counts as those members' consequence.
    • A record that names nothing, or names an OK member, is its own cause.
    • The composite's row keeps its level and message. Only the chip's count and the attention list change.
  • Precedent:
    • AUTOSAR DEM files a failure as a CONSECUTIVE FAULT when a parent component is already FAILED, and does not store it (SWS_Dem_01127, 01130). It also allows a DAG of dependencies, not a tree (01120, CONSTR_06106).29
    • Boeing's central maintenance computer screens out cascaded faults.36
    • Icinga's --blame --root-cause.32
    • Alertmanager's inhibit_rules.33
  • Why not a second tree edge: membership lives on the composite's records. The rig composes things scattered across the connectivity tree (2 adapters, 7 boards, 2 cameras, the PC). ros2_medkit's areas and functions are the same kind of cross-cutting group.5162

The five proposals

P1 · Wrapper plugins: every composite is a driver

A rig (or arm, or spider) is a plugin like moteus_servo, with the same describe | diagnose | act CLI. It reads its members' latest records and writes its own. The verdict is code, owned by whoever owns the composite. This is closure under composition taken literally: a composite is a black box like any leaf.

{"record": "status", "path": "host/rig-1-dof-test-rack", "name": "1-DOF test rack: actuators",
 "level": "warn", "code": "BoardOut", "caused_by": ["host/usb1/1-5/can/15"],
 "message": "6/7 boards: CAN 15 out; single-joint tests on the other six still run"}
# rule in code: one board out -> WARN · CAN 1 out (hard stop + gravity load) or any adapter out -> ERROR
Record v0.1 / black box
The purest fit. The schema gains only caused_by. The plugin protocol gains a records input; today a plugin gets --device only.
Computer
The computer plugin is one more leaf. A wrapper may read it, for example "recording unavailable: disk".
Dev vs deployment
At the bench, pytest calls the wrapper's diagnose() on the F1–F3 fixtures. On site, the host runs it every period. There is no readiness unless every wrapper writes its own.
Stock parts
ROS diagnostic_updater composite tasks26, Apex.Grace fault monitors7, ROS self_test for the on-demand part60, and the existing plugin protocol.
Failure modes
  • Every composite re-implements counting, staleness and "not run". bam_diagnostics fell into exactly this: a check that never ran was reported as OK, "SKIPPING".16
  • Arrival skew. Members report at different times, so the wrapper flaps. Your Oct 23 health-bar note makes the same point.14
  • A crashed wrapper reads STALE while every leaf is fine.
  • The reasoning is invisible on the page.
  • You need one wrapper per rig.

P2 · Rollup groups as data: the ROS aggregator's analyzers

One file declares groups and how their members combine. It uses the ROS diagnostic_aggregator analyzer schema plus Icinga Business Process operators. The host computes each group's own record. The groups only combine levels: there are no thresholds.

                 regex: "can/(1|11|12|13|14|15|21)$", num_items: 7}

P3 · The expected setup becomes the acceptance spec: one file, three run modes recommended

Keep everything expected.toml has. Add [[rig.check]] entries that each name the status they read, a pass condition and when they run. The three modes are aerospace's built-in-test modes35:

  • startup (power-on BIT): boot, plug and replug, read-only;
  • continuous (CBIT): judged on every fresh driver report;
  • initiated (IBIT): a person's click runs the action. The result is kept and expires.

Readiness is a separate state from pass/fail, as in OBD-II: ran, not run since boot, or not run since a change.3738

[[rig]]
name = "1-DOF test rack"
# ... the [[rig.device]] entries exactly as today ...

[[rig.check]]
name = "firmware current"
when = "startup"                 # every boot, plug and replug; reads only
reads = "can/*: firmware"         # each expected board's own firmware status
pass = "ok"                       # i.e. no UpdateAvailable

[[rig.check]]
name = "reply loss"
when = "continuous"              # judged on the reports the drivers already send
reads = "can/*: servo"
pass = "reply_loss < 1 %"

[[rig.check]]
name = "comms sweep"
when = "initiated"               # a person's click: check_comms on both adapters (query)
action = "check_comms"
valid_for = "24 h"
invalidated_by = ["Restarted", "Plugged", "firmware"]

[[rig.check]]
name = "CAN 12 pendulum tracking"
when = "initiated"
action = "tape"                  # bam_rack_twin hardware tape: MOVES, never scheduled
pass = "tracking_rms < 0.5 deg"
valid_for = "7 d"

[computer]                       # thresholds as data; defaults = ROS diagnostic_common_diagnostics
cpu_warn = "90 %"
memory_warn = "90 %"
disk_free_warn = "5 %"
disk_free_error = "1 %"
usb3_links = 2                   # both D405s at 5000 Mb/s

[profile.twin]                   # the same checks on the MuJoCo twin, wider where physics differs
tracking_rms = "< 1.0 deg"
Record v0.1 / black box
  • Each check is a status on the rig entity, with source: io_diagnostics.expected and caused_by naming the members it read.
  • Not run is unknown with code CheckNotRun, the twin of today's ExpectedNotChecked.
  • An initiated result never goes stale, but it expires:
    • after valid_for, IEC 61508's proof-test interval39;
    • on an invalidated_by event. In OBD, clearing codes resets readiness37; in DEM, re-enabling an event sets "test not completed" (0x50)29.
  • Expectations are the consumer's, as in consumer-driven contracts4243. So they live on the rig's row, and a board's row stays its own self-report. Today's RatioMismatch on the board moves to the rig (decision 2 below).
  • Later, a node's pass condition can default from its part's robotparts diagnostics slot (ok_range).24
Computer
  • [computer] sets the host leaf's thresholds, and rig checks can read it (usb3_links).
  • On this PC, k10temp Tctl has no chip limits, and Zen 4 is designed to sit at its 95 °C limit under load. So CPU temperature warns on sustained throttling, not on a fixed number.5558
  • The NVMe drive reports max 82 / crit 85 °C, used as given.
Dev vs deployment
io-diagnostics accept --rig "1-DOF test rack" --profile bench|site|twin:
  • runs the startup and continuous checks now;
  • lists the initiated checks, with their dry-run tokens, for a person to run;
  • prints JUnit and exits with a Nagios code.
That is Goss's split: validate at dev, serve → /healthz at deploy, one file.44 It is also the factory/site acceptance pair (IEC 62381: FAT, FIT, SAT, SIT).40
Stock parts
  • Goss; InSpec controls (impact, only_if → N/A).46
  • OpenHTF measurement validators (in_range; outcomes PASS / FAIL / UNSET / SKIPPED; marginal).47
  • OBD readiness; DEM; the IEC 61508 proof test.
  • Kubernetes startup vs liveness probes.41
Failure modes
  • pass grows into a mini-language. Cap it at "measurement op value", with no expressions.
  • The file lives in ~/.config, so the copy a site runs needs a committed twin.
  • There are two manifests for one rack: deployment.json already holds UUIDs and firmware history.23
  • Validity windows can nag.
  • A twin pass is not a site pass, so the profile must show on the row.

P4 · The acceptance suite is code, and its results are records

Rig-level checks are pytest tests in the rig's repo, marked with their entity, mode and validity. A pytest plugin turns each result into a status: pass → ok, fail → error, skip → unknown NotRun, plus typed measurements. Development runs pytest. The robot runs the same suite on a timer (passive marks) or on a click (marks that move hardware).

# bam_ws/src/dev/bam_rack_acceptance/tests/test_one_dof_rack.py
from robotdiagnostics.testing import diagnostic      # pytest plugin: results -> diagnostics-record/0 lines

@diagnostic(entity="rig:1-DOF test rack", when="startup")
def test_every_expected_board_answers(rig):
    assert rig.answering("can/*") == rig.expected("can/*")       # names the missing one

@diagnostic(entity="rig:1-DOF test rack", when="initiated", moves=True, valid_for="7d")
def test_can12_pendulum_tracking(rig, measure):
    run = rig.act("can/12", "tape", profile="slow")              # a person confirms the token
    measure("tracking_rms", run.rms_deg, unit="deg", error_high=0.5)

Dev vs deployment

Stock parts

  • Testinfra --nagios.45
  • OpenHTF phases, plugs, measurements, and its test record with dut_id and station_id.47

P5 · Capability gates: the top level answers "what can I do now?"

Instead of a colour per composite, declare a handful of named capabilities, each a set of required checks. The top of the page lists which are available and, for each one that isn't, its one cause. The actions' existing preconditions (port_free, board_answers, bus_lock_free) are the first capabilities.

Recommendation and tracer bullet

Build P3, on the caused_by seam.

  • Keep P1 as the escape hatch the record already allows. A composite whose verdict can't be written as data gets a wrapper plugin.
  • Borrow ROS's "Expected N, found M" wording from P2, and a pytest fixture from P4, so the bench gate is literally pytest.
